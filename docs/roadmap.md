# Emerald 项目路线图（Post-v0.4.0）

> **文档定位**：Emerald 自 v0.4.0（2026-07-03）发布之后的战略路线图。
>
> **时间策略**：**不锁死日历时间**，按依赖顺序排列；工作量以"人周"为单位估算。
>
> **依赖基线**：所有估算假设 1 名全职工程师（senior level），并行工作按主题划分。
>
> **更新触发**：每完成一个里程碑、或外部条件（如 Supermemory 新版本、Python 生态变化）发生重大变化时，重新审视本路线图。
>
> **⚠️ 2026-08-09 审视重标定**：项目审视决议落地（详见 `docs/adr/0001`、`0002`、`0003`）：① 北极星从「≥ Supermemory 的 80%」改为独立度量体系（§1.3）；② v0.5.0（M2）范围重新裁剪（§四 M2）；③ out-of-scope #2 修正——web UI 是产品层，插件生态不在范围（§七）；④ 新功能须过「功能三问」立项 gate（AGENTS.md 开发指南 #11）。
>
> **⚠️ 2026-08-10 M2 范围决策落地**：经 Wayfinder Map（issue #8）全票决议，M2 范围细化为「测试卫生 → 质量套件 → 绝对分报告 → 安全审计」并逐项锁定通过标准（§四 M2）；SLA 性能验证整体延后，不再属于 v0.5.0。

## 一、愿景与战略原则

### 1.1 一句话愿景

> **让 Emerald 成为「私有化部署、可生产使用、与 Supermemory 能力对齐」的 AI Agent 记忆基础设施首选。**

### 1.2 战略原则（继承自 AGENTS.md）

| # | 原则 | 路线图含义 |
|---|---|---|
| 1 | **记忆 ≠ RAG** | 不为对齐 Supermemory 而牺牲图谱独立性 |
| 2 | **图谱优先** | 多跳推理、NER 等深度能力优先于纯向量优化 |
| 3 | **全自动** | 路线图中所有面向用户的能力都必须保持"零配置" |
| 4 | **同一个上下文池** | 任何 SDK/框架集成必须复用同一 entity_id |
| 5 | **时序完整性** | 任何检索路径都不能破坏时序语义 |
| 6 | **按类型分块** | 多模态提取持续投入，不为简单化而牺牲 |
| 7 | **提取，而非存储** | LLM 提取是核心路径，不是可选优化 |

### 1.3 路线图成功的 3 个北极星指标

| 指标 | 当前（v0.4.0，2026-07-03 发布） | 目标（v0.8.0） |
|---|---|---|
| **独立度量体系** | 合成场景 + mock 嵌入 4/6 通过；无公开报告 | 套件全绿（时序正确性 / 遗忘有效性 / 图谱精度）+ 真实嵌入绝对分报告公开 + SLA 达成（画像 <100ms、搜索 P50/P99） |
| **生产部署就绪度** | Productionizing 70%（生产化进行中，见 production-readiness 评估） | GA（生产 SLA 保障） |
| **开发者采用度** | 2 SDK（Python + TypeScript）+ Pandaria 集成 | 4 SDK（Python/TS/Java/Go）+ 5 框架集成 |

## 三、4 个战略主题（并行工作流）

每个主题都有独立的目标、成功指标和工作量。**主题之间在某些节点存在依赖**，但大多数工作可以并行。

### 主题 A：生产加固（Production Hardening）

**目标**：Emerald 可以被任何中型企业在生产环境部署并稳定运行。

| 工作项 | 工作量 | 依赖 | 阻塞谁 |
|---|---|---|---|
| **A1.** Dockerfile production stage 独立 `pip install --no-cache-dir` | 1-2 天 | 无 | 主题 D（负载测试） |
| **A2.** Kubernetes manifest 实操验证 + 故障恢复演练 | 1 周 | A1 | 主题 D |
| **A3.** v2 API 实质改进：分页 + 限流 + `customId` 幂等 + 业务错误码体系 | 2 周 | 无 | 主题 C（SDK） |
| **A4.** 分布式追踪（OpenTelemetry，跨 Neo4j/Postgres/Redis/LLM） | 1 周 | 无 | 主题 D |
| **A5.** API 文档 overhaul（OpenAPI 完整、教程、SDK 对照） | 2 周 | A3 | 主题 C |
| **A6.** 安全审计（依赖扫描、secret 检测、pen test 模拟） | 1 周 | A1 | v0.8.0 |
| **A7.** 生产级日志脱敏（PII 自动检测、敏感字段屏蔽） | 1 周 | A4 | A6 |

**主题 A 总计**：~7-8 人周

## 七、明确不在范围内（Out of Scope）

为防止范围蔓延，明确以下事项**不在本路线图内**：

1. ❌ **多租户 SaaS 化**：本路线图聚焦私有化部署，不做 Emerald-as-a-Service
2. ❌ **消费者插件生态**：浏览器扩展、Raycast 等 Supermemory 已有的产品形态。**web UI 除外**——它是私有化部署的产品层（ADR-0003），在本范围内
3. ❌ **企业 SSO/SAML 集成**：当前 API Key 认证足够，后续按需添加
4. ❌ **图数据库替换**：不引入新的图数据库选项（如 SurrealDB）
5. ❌ **多模态输出**：Emerald 是记忆基础设施，不做图像/视频生成
6. ❌ **Agent 编排**：不与 LangGraph / CrewAI 直接竞争，仅做记忆提供方
7. ❌ **记忆迁移工具**：不做从其他系统（如 Mem0、Letta）迁移的工具
8. ❌ **Java/Go/Rust 后端重写**：C5 Java SDK 仅是 SDK，不重写后端

## 十、附录：版本号约定

### 10.1 阶段性版本语义

遵循语义化版本（SemVer），但对每个阶段有明确的承诺边界：

| 版本号 | 阶段 | API 承诺 | 适用场景 |
|---|---|---|---|
| v0.4 - v0.7 | 能力构建期 | **可能破坏性变更**；不保证兼容 | 内部测试、概念验证、合作伙伴早期集成 |
| **v0.8** | **Production-Ready Beta** | **趋于稳定**；仍可能变更 | **建议生产部署**；但需接受偶发 API 调整 |
| v0.9 | Release Candidate | API 冻结；仅修 bug | 最后修复窗口；锁定 GA 接口 |
| v1.0 | GA | **12 个月向后兼容承诺** | 严肃生产系统；长期维护承诺 |
| v1.x | 持续演进 | 向后兼容；增量功能 | 长期支持 |

### 10.2 v1.0 提升的硬性条件（不在本路线图内）

v1.0.0 是重大承诺事件，**不会**因功能完成自动触发。必须在满足**全部**以下条件后单独评估：

| # | 条件 | 验证方法 |
|---|---|---|
| 1 | v0.8.0 / v0.9.0 在 ≥ 2 个真实生产环境运行 ≥ 3 个月 | 部署清单 + 客户访谈 |
| 2 | API 在最近 3 个 minor 版本内**未发生**破坏性变更 | git history 审查 |
| 3 | 独立度量套件全绿 + 绝对分数报告公开（ADR-0001） | `docs/benchmarks/` 实测报告 |
| 4 | TypeScript SDK + 至少 2 个框架集成被实际项目使用 | npm 下载量 + GitHub issues |
| 5 | 安全审计 0 个 P0/P1 漏洞 | 独立审计报告 |
| 6 | 至少 1 个公开承诺的 SLA 文档 | 已发布的 SLA |
| 7 | 核心团队对 API 演化路径有 12 个月可见性 | 公开 RFC / ADR |

**任何一条不满足，v1.0 不发布。** v0.9.0 可以无限期延后，直到团队对 API 稳定性有充分信心。

### 10.3 本路线图的版本边界

- **起点**：v0.4.0（2026-07-03 发布）
- **终点**：v0.8.0（Production-Ready Beta）
- **不包含**：v0.9.0（RC）、v1.0.0（GA）—— 这两个版本**需要在 v0.8 真实使用数据的基础上单独决策**

v1.0 之后的路线图将在 v1.0 实际发布前 1-2 个月单独制定。
